# 报告二:技能/知识/工具 → 上下文 → 装配 → 规划 → 执行(2026-08-01)

## 一句话回答你的问题

**不是「先问模型要个规划」。** 规划分两层,本系统两层都已经实现,而且刻意不在同一层做:

| 层 | 做法 | 本系统实现 | 要不要规划 |
|---|---|---|---|
| 编排层 | 把**编排清单**给模型,让它排调用顺序 | `autoflow.plan()` | **要** |
| 节点内 | 技能/知识渐进披露 + tool-calling 循环 | `agent_runtime.run()` | **不要** |

**画布节点内不该再让模型规划——画布本身就是人写好的规划。** 在画好的图里再规划一次,
等于两个规划打架。

## 本系统现状(已实现,`agent_runtime.assemble`)

三样东西进上下文的**位置各不相同**,这是关键:

- **技能 → 渐进披露**。系统提示词里只放 `slug + name + description`(SKILL.md
  frontmatter 那两行),模型自己判断哪个适用,再调 `skill.read` 读全文。
  理由:技能多了全量塞不下,而 description 本来就是写给模型做触发判断的。
- **知识 → 只圈范围,不预塞**。系统提示词里只列文件夹名,模型调 `kb.search` 检索。
- **工具 → function schema 常驻**。来自 `services/tools.py` 统一注册表(工作流 action、
  技能工具、规划器共用一套,不另起第二套)。

执行是标准 tool-calling 循环(上限 12 步),模型不再要工具时那条 content 就是产物。
**工具失败回喂给模型自我修正,不中断**——这条很重要,失败即中断会让链路极脆。

### 一条血泪经验,别丢

`inject_ctx` 里写着:**运行上下文强制覆盖模型给的值,不是「空了才填」**。
实测模型会自己编一个 `project_id: 23`(真实是 25),然后一路查空、回「要素不存在」,
而表面上工具调用是成功的。

> 模型没资格猜自己在哪个项目上干活。用户在界面上选定的就是事实。

任何新加的上下文引用机制都必须守住这条。

### 规划器怎么做的

`autoflow.plan()`:任务 + 编排清单(`slug|name|description|需要的上下文|批量维度`)
→ 模型输出 JSON `{"plan":[{"flow":"slug","reason":"…"}]}`。约束:只能选清单里的 slug、
不排前置(编排自己会递归跑前置)、最多 6 步、上下文没给全的编排不许排。

### 为什么不用 Claude Agent SDK / Google ADK

本项目模型层是 OpenAI 兼容的(`models_registry` 配 base_url/api_key/model),
那两家要求规划引擎走自家 API,等于跟出图出视频的模型分家。而工具已经是本地 Python
函数,循环本身不到百行。

## 行业通行做法(与本系统对照)

按「东西的性质」决定它进上下文的位置,这是行业共识:

| 性质 | 放哪 | 常驻? |
|---|---|---|
| 我是谁、怎么做事 | system prompt | 常驻 |
| 能力/方法论(技能) | frontmatter 常驻,正文按需读 | 渐进披露 |
| 事实(知识库/数据) | 检索后注入 user 段 | 按需 |
| 动作(工具) | function schema | 常驻,但几十个以上要分组/路由 |

两种执行范式,本系统各用在合适的层:
- **ReAct / tool-calling 循环**(边想边做):步骤不确定时用 → 节点内
- **Plan-and-Execute**(先规划后执行):可预算、可审计、可人工确认,花钱的动作用 → 编排层

本系统的做法与主流一致,渐进披露那条尤其正确(技能规模化的唯一解)。

## 回答:LLM 属性面板要不要加「+ 上下文引用」

**要,但必须分清两类,而且引用要进 user 段而不是 system 段。**

| 类型 | 例子 | 编排时定 / 运行时才有 | 现状 |
|---|---|---|---|
| 静态能力 | 技能、知识库文件夹、工具 | 编排时 | ✅ 已有 |
| **动态上下文** | 上游节点产物、项目/章/镜/要素实体 | 运行时 | ❌ 缺,就是图 2 那个「+」 |

建议形态——系统提示词下方一行 `+ 引用`,三类:

1. `@上游节点` → 插入 `{{节点.字段}}`(引擎按连线校验合法性)
2. `@运行上下文` → 插入 `{{ctx.project_id}}` 等(`agent_runtime.fill` 已支持
   `{{ctx.*}}` / `{{item.*}}`,**不用新写**)
3. `@取数工具` → 声明前置调用(如 `project.info`),结果拼进上下文段

### 一条硬规矩:引用进 user 段,不进 system 段

system 是稳定的「你是谁、怎么做」,每次运行都一样,所以 charter 可复用、
prompt 缓存可命中。上下文每次不同,塞进 system 会同时毁掉这两点。
`agent_runtime.run()` 现在正是这么分的(`system=assemble(...)`, `user=task`),
面板设计别把它拧回去。

## 落到属性面板上,一个 LLM 节点该配什么

```
系统提示词  charter          ← 稳定,项目无关,可复用
  + 引用    上游/上下文/取数  ← 每次运行不同,进 user 段
技能        skills           ← 只给名+简述,模型自己 skill.read
知识库      folder_ids       ← 只圈范围,模型自己 kb.search
工具        tool_names       ← function schema
缺才跑      only_missing     ← 判据来自 writes 声明
质检        qc_* (见报告一)
```

除了「+ 引用」这一项,其余**后端全部现成**,面板是把已有能力暴露出来,不是新建能力。
